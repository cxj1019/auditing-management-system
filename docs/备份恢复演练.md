# 备份恢复演练指引

> 目的：证明备份真的可恢复。恢复能力 = 灾备的全部意义，只备份不演练等于没备份。

## 系统备份是什么
- 每日 02:30 自动 + 管理员可手动触发（系统设置 → 数据备份）
- ZIP 内容：21 张业务表 JSON + **附件原文件**（`files/` 目录，函证/合同/发票/报销/付款全部附件）
- 存储在 Supabase 对象存储 `backups/` 前缀下，保留最近 7 天

## 演练步骤（每月一次，5 分钟）

```bash
cd tools
# 1. 自动下载最新备份并恢复到独立 schema（不碰 public 生产数据）
py -X utf8 backup_restore_drill.py --from-storage

# 2. 或使用手动下载的 ZIP
py -X utf8 backup_restore_drill.py --zip 备份文件.zip

# 3. 想人工检查恢复出来的数据时保留 schema
py -X utf8 backup_restore_drill.py --zip xx.zip --keep
```

脚本做四件事：下载/读取 ZIP → 在独立 schema 里按 public 表结构建表 → 逐表灌数 → **逐表行数校验**（与备份 JSON 条数比对）。

## 通过标准
- 21 张表全部显示 `✓ N/N 行一致`
- `files/` 目录有附件文件（脚本控制台会打印附件数量）

## 最近一次演练
- 日期：2026-10-04
- 备份：backup-2026-10-04-1791138608417.zip（114 KB，5 个附件）
- 结果：**21/21 表行数全部一致**（含 sys_menu 75 行、sys_role_menu 220 行、vendor_payment 44 行、reimbursement 29 行）

## 真实灾难恢复步骤（当生产库不可用时）
1. 从 Supabase 存储（或异地副本）取最近备份 ZIP
2. 准备一个空 PostgreSQL（新 Supabase 项目/自建），先启动一次应用让 Flyway 建全表结构
3. 用本脚本 `--schema public` 恢复数据（注意：此时目标是新库的 public，脚本防呆会拒绝对当前生产库执行）
4. 附件：解压 ZIP 的 `files/` 目录，按路径上传到新 Supabase 存储桶同名前缀
5. 应用环境变量指向新库，验证登录与关键页面

## 防呆说明
- 脚本拒绝向 `public` schema 恢复（防止误覆盖生产），演练默认独立 schema、结束自动清理
- 演练连接串内置（只读演练），真实恢复时改脚本顶部 DB 配置为目标库
